마이 아이: 출시 앱에서 마주친 구조와 운영 문제

MY-01 · Architecture

화면 코드와 Firebase 코드가 얽힌 구조를 layer로 나눠 변경과 테스트가 쉬운 구조로 바꿨습니다.

문제 상황
  • 처음 구조는 화면, 데이터 모델, Firebase 통신 코드가 한 앱 안에 함께 들어가 있었습니다.
  • 홈 타임라인을 고치려면 Firebase 저장 방식까지 같이 봐야 해서 수정 범위가 쉽게 커졌습니다.
  • 수유, 배변, 수면 같은 기록도 하나의 큰 모델에 섞이면 어떤 값이 필요한 기록인지 매번 확인해야 했습니다.
설계 방향
  • 기존 코드를 한 번에 갈아엎기보다, 레거시 코드를 보존한 채 새 구조로 옮기는 방식을 선택했습니다.
  • layer 기준으로 화면은 Features, 규칙은 Domain, 외부 연동은 Clients로 분리했습니다.
  • Firebase는 앱 곳곳에서 직접 부르지 않고, Clients 계층을 통해서만 접근하도록 제한했습니다.
구현 근거
  • 육아 기록은 CareEvent로 표현해 수유, 배변, 수면처럼 기록별로 필요한 값이 드러나게 했습니다.
  • 화면은 CareRecordClient 같은 인터페이스만 알고, 실제 Firestore 저장 방식은 Clients 구현 안으로 숨겼습니다.
  • 홈 화면은 기록을 불러오고 추가하는 동작만 요청하므로, Firebase 타입을 몰라도 동작을 검증할 수 있습니다.
결과 또는 검증
  • 화면, 도메인 규칙, Firebase 구현, 디자인 시스템을 서로 다른 타깃으로 나눴습니다.
  • Firebase를 직접 아는 코드는 Clients 쪽에만 남겨 화면 코드의 변경 부담을 줄였습니다.
  • 새 기록 타입을 추가할 때도 화면 전체를 훑기보다 기록 모델과 홈 기능 중심으로 수정 범위를 좁힐 수 있게 됐습니다.
Features / Home 화면은 기록 동작만 요청 타임라인 표시, 빠른 기록 추가, 삭제 요청
→
Domain 기록 규칙과 계약을 정의 CareEvent, CareRecordClient, BabyClient
→
Clients Firebase 구현을 담당 Firestore, Auth, Crashlytics, Analytics
핵심 변화 홈 화면은 Firebase 타입을 직접 알지 않아도 동작하고, 실제 저장 방식은 Clients에서 교체하거나 검증할 수 있습니다.

MY-02 · Performance

여러 화면에서 같은 사진을 요청해도 한 번만 내려받고, 캐시된 이미지는 첫 프레임부터 보이게 했습니다.

문제 상황
  • 아기 프로필, 일지, 양육자 목록에서 같은 Firebase Storage 사진을 반복해서 보여줘야 했습니다.
  • 화면마다 이미지를 따로 요청하면 같은 URL도 여러 번 다운로드되고, 진입 첫 순간에는 placeholder가 다시 보였습니다.
  • 사진을 업로드한 직후에도 새 download URL 기준 캐시가 없으면 방금 고른 사진을 다시 네트워크에서 받아야 했습니다.
설계 방향
  • Kingfisher나 SDWebImage를 붙일 수도 있었지만, 필요한 범위는 Firebase Storage URL의 Data 캐시였습니다.
  • 외부 라이브러리보다 앱 안에서 통제 가능한 작은 캐시 계층을 만드는 쪽을 선택했습니다.
  • 동시 요청을 안전하게 합치기 위해 캐시 중심 객체는 actor로 만들었습니다.
구현 근거
  • CachedAsyncImage는 초기화 시점에 동기 캐시를 먼저 확인해, 이미 본 이미지를 첫 프레임부터 표시합니다.
  • URLDataCache는 Memory → Disk → 진행 중인 Task → Network 순서로 조회합니다.
  • StorageClientLive는 업로드 직후 원본 Data를 새 download URL 키로 바로 저장합니다.
결과 또는 검증
  • 같은 URL을 여러 화면이 동시에 요청해도 진행 중인 Task 하나를 공유합니다.
  • 이미 본 이미지는 화면 진입 시 placeholder 없이 바로 표시됩니다.
  • 업로드 직후에도 새 URL에 원본 Data가 연결되어 불필요한 재다운로드를 줄였습니다.
Image View 화면은 URL 이미지를 요청 프로필, 일지, 양육자 목록의 CachedAsyncImage
→
URLDataCache actor 같은 요청을 하나로 수렴 Memory → Disk → In-flight Task 순서로 확인
→
Firebase Storage 캐시 미스일 때만 다운로드 업로드 직후에는 download URL 키로 원본 Data 저장
핵심 변화 이미지 표시 흐름이 각 화면마다 흩어지지 않고 하나의 캐시 actor로 모여, 중복 다운로드와 첫 프레임 깜빡임을 줄였습니다.
Core Code 동시 요청은 진행 중인 Task를 공유하고, 캐시된 이미지는 초기 상태로 바로 주입했습니다.

URLDataCache: 같은 URL 요청 합치기

public actor URLDataCache {
  private var inflightFetches:
    [URL: Task<Data, Error>] = [:]

  public func data(for url: URL) async throws -> Data {
    if let cached = URLDataMemoryCache.shared
      .data(for: url) { return cached }

    if let diskData = readFromDisk(for: url) {
      return diskData
    }

    if let existing = inflightFetches[url] {
      return try await existing.value
    }

    let task = Task {
      try await fetchAndStore(url: url)
    }
    inflightFetches[url] = task
    defer { inflightFetches[url] = nil }
    return try await task.value
  }
}

public init(url: URL?) {

private func load() async {

  } catch {

  }
}

MY-03 · Data Consistency

누가 아이 기록을 볼 수 있는지 앱 화면과 Firebase 보안 규칙이 같은 보호자 목록으로 판단하게 했습니다.

문제 상황
  • 레거시 구조는 Baby.caregivers, Caregiver.babies를 DocumentReference 배열로 들고 있었습니다.
  • 가족 초대, 탈퇴, 아기 목록 표시에서 참조를 각각 따라가면 삭제되거나 남아 있는 stale reference를 계속 정리해야 했습니다.
  • 기록, 울음 분석, 노트, 사진, 일정 알림도 모두 같은 가족 권한 판단이 필요했습니다.
설계 방향
  • 클라이언트에서 깨진 참조를 계속 청소하는 방식은 문제를 늦게 발견할 뿐, 권한의 기준이 되기 어렵다고 봤습니다.
  • Firestore Rules와 Cloud Functions에서도 바로 읽을 수 있는 UID 문자열 배열을 기준으로 잡았습니다.
  • mainCaregiverID는 소유자 역할, caregiverIDs는 가족 구성원 권한으로 분리했습니다.
구현 근거
  • Baby 모델은 mainCaregiverID와 caregiverIDs: [String]을 직접 가집니다.
  • 신규 등록은 현재 사용자 UID를 배열에 넣고, 초대와 탈퇴는 arrayUnion, arrayRemove로 갱신합니다.
  • 아기 목록은 whereField("caregiverIDs", arrayContains: uid) 한 조건으로 조회합니다.
결과 또는 검증
  • 사용자가 접근 가능한 아기 목록을 사용자 문서의 Reference 순회 없이 한 번의 쿼리로 가져옵니다.
  • records, cryRecords, notes Firestore Rules가 같은 caregiverIDs를 권한 키로 사용합니다.
  • Storage 사진 권한과 일정 push 대상도 같은 배열을 사용해 화면, 저장소, 서버 로직의 기준을 맞췄습니다.
Baby Document 가족 권한의 단일 기준 mainCaregiverID, caregiverIDs
→
App Clients 조회·초대·탈퇴가 같은 필드 갱신 arrayContains, arrayUnion, arrayRemove
→
Rules / Functions 기록·사진·알림 권한에 재사용 records, cryRecords, notes, Storage, push
핵심 변화 가족 구성원 판단을 참조 객체 순회가 아니라 UID 배열 하나로 모아, 앱 화면과 보안 규칙이 서로 다른 기준을 보지 않게 했습니다.
Core Code 조회, 초대, 탈퇴, 보안 규칙이 모두 caregiverIDs를 기준으로 동작합니다.

CG-01 · Concurrency

STT 요청을 Repository 내부에서 FIFO로 직렬화해 동시 호출을 실패가 아닌 대기 상태로 처리했습니다.

문제 상황
  • 녹음이 끝나면 분석 서비스가 음성 파일을 전사하고, 전사 결과가 만들어지면 요약 단계로 이어지는 구조였습니다.
  • 짧은 녹음을 연속으로 저장하면 앞 전사가 끝나기 전에 다음 transcribe 호출이 들어올 수 있었습니다.
  • 외부 음성 인식 자원이 겹치면 실제 음성 파일 문제가 아닌데도 .transcriptionFailed 상태로 저장될 수 있었습니다.
설계 방향
  • 화면에서 버튼을 막는 방식은 백그라운드 분석, 재시도, 자동 큐잉 같은 진입점을 모두 막지 못합니다.
  • 호출 측에 재시도 로직을 두면 STT 자원 점유 정책이 여러 계층으로 퍼집니다.
  • 그래서 STTRepository actor가 슬롯을 소유하고, 들어온 요청을 FIFO 순서로 기다리게 했습니다.
구현 근거
  • DefaultSTTRepository는 isBusy와 waiters 큐를 actor 내부 상태로 가집니다.
  • transcribe 시작 시 acquireSlot()을 호출하고, 종료 시 defer releaseSlot()으로 다음 요청을 깨웁니다.
  • 대기 중 취소된 요청은 cancelWaiter에서 큐에서 제거해 불필요한 전사를 시작하지 않게 했습니다.
결과 또는 검증
  • 동시에 들어온 전사 요청은 첫 작업이 끝날 때까지 실패로 떨어지지 않고 대기합니다.
  • 분석 서비스 입장에서는 transcribe 호출만 유지하면 되어, 큐잉 정책이 화면이나 UseCase로 새지 않습니다.
  • .transcribeFailed는 단순 자원 경합이 아니라 실제 인식 실패에 가까운 신호로 남게 됐습니다.
Analysis Service 전사 요청을 시작 voiceNoteID별 Task를 만들고 STTRepository.transcribe 호출
→
STTRepository actor 한 번에 하나만 실행 isBusy, waiters, acquireSlot, releaseSlot
→
Speech Resource 외부 인식 작업을 보호 SFSpeechURLRecognitionRequest, SFSpeechRecognitionTask
핵심 변화 동시 호출을 호출자 실패로 돌리지 않고, STT 자원을 감싼 Repository가 순서를 보장하도록 책임을 모았습니다.
Core Code 전사 시작 전 슬롯을 확보하고, 작업 종료 시 다음 대기자를 FIFO로 깨웁니다.

DefaultSTTRepository: 전사 작업 직렬화

public actor DefaultSTTRepository: STTRepository {
  private var isBusy = false
  private var waiters: [Waiter] = []

  public func transcribe(
    audioFilePath: String
  ) async throws -> Transcript {
    try await acquireSlot()
    defer { releaseSlot() }

    let url = storageService
      .absoluteURL(for: audioFilePath)

    return try await withCheckedThrowingContinuation {
      try startRecognitionTask(
        audioFileURL: url,
        continuation: $0
      )
    }
  }
}

Slot Queue: 대기자 인계와 취소 처리

private func acquireSlot() async throws {
  if !isBusy {
    isBusy = true
    return
  }

  let granted = await waitInQueue()
  if !granted { throw .cancelled }
}

private func releaseSlot() {
  guard !waiters.isEmpty else {
    isBusy = false
    return
  }

  waiters.removeFirst()
    .continuation.resume(returning: true)
}

CG-02 · Analysis Lifecycle

분석 취소·이탈 상황에서도 완료된 결과는 보존하고, 진행 중 상태만 정리했습니다.

문제 상황
  • 음성 메모 분석은 pending → transcribing → transcribed → summarizing/regenerating → completed로 이어집니다.
  • 전사나 요약 Task가 실행 중일 때 사용자가 분석을 취소하거나 앱을 종료할 수 있습니다.
  • 전이 상태가 DB에 남으면 화면은 계속 로딩으로 보이고, 취소를 실패로 처리하면 이미 만들어진 전사·요약 결과까지 흔들릴 수 있었습니다.
설계 방향
  • ViewController 생명주기에만 맡기면 화면 밖에서도 계속 도는 분석 Task를 안정적으로 정리하기 어렵다고 봤습니다.
  • 취소 시 DB를 다시 추론하는 방식보다, Task를 시작한 서비스가 이전 안정 상태를 함께 들고 있는 방식이 명확했습니다.
  • 그래서 VoiceNoteAnalysisService가 진행 중 Task와 previousState를 함께 보관하고, 취소·정상 종료 경로에서만 상태를 되돌리게 했습니다.
구현 근거
  • startTranscription, startSummarization은 먼저 transcribing, summarizing, regenerating 같은 전이 상태를 저장합니다.
  • entries에는 voiceNoteID별 Task와 previousState를 함께 저장해 어떤 상태로 되돌릴지 잃지 않게 했습니다.
  • revertState는 현재 상태가 전이 상태일 때만 previousState로 되돌려 completed, transcribed 같은 결과 상태를 건드리지 않습니다.
결과 또는 검증
  • AppDelegate의 applicationWillTerminate에서 cancelAll()을 호출해 앱 종료 시 진행 중인 분석을 한 번에 정리합니다.
  • 취소된 Task는 실패 상태를 저장하지 않고, 이전 안정 상태로 되돌아가 화면이 무한 로딩에 머무르지 않게 했습니다.
  • 이미 저장된 transcript, summary는 상태 복구 과정에서 덮어쓰지 않아 결과 보존과 상태 정리를 분리했습니다.
핵심 변화 전사·요약 결과 데이터는 건드리지 않고, 화면을 무한 로딩으로 만드는 진행 상태만 정리합니다.
Core Code 진행 중 Task와 이전 상태를 함께 저장하고, 취소 시 전이 상태만 되돌립니다.

VoiceNoteAnalysisService: Task와 previousState 보관

@MainActor
public final class DefaultVoiceNoteAnalysisService {
  private struct Entry {
    let task: Task<Void, Never>
    let previousState: AnalysisState
  }

  private var entries: [UUID: Entry] = [:]

  private func startTranscription(
    for voiceNote: VoiceNote,
    previousState: AnalysisState
  ) {
    persist(voiceNote: voiceNote, analysisState: .transcribing)

    let task = Task { /* STT 실행 */ }
    entries[voiceNote.id] = Entry(
      task: task,
      previousState: previousState
    )
  }
}

cancelAll / revertState: 전이 상태만 되돌리기

public func cancelAll() {
  let snapshot = entries
  entries.removeAll()

  for (id, entry) in snapshot {
    entry.task.cancel()
    revertState(
      voiceNoteID: id,
      to: entry.previousState
    )
  }
}

private func revertState(
  voiceNoteID: UUID,
  to previousState: AnalysisState
) {
  guard let current = fetch(voiceNoteID) else { return }

  switch current.analysisState {
  case .transcribing, .summarizing, .regenerating:
    persist(voiceNote: current, analysisState: previousState)
  default:
    break
  }
}

HM-01 · SpriteKit Lifecycle

블록이 실제로 닿은 뒤 성공/실패를 판단하고, 게임을 나가면 남은 동작도 함께 멈추게 했습니다.

문제 상황
  • 사용자가 탭하면 움직이던 블록이 아래로 떨어지고, 이전 블록 위에 제대로 올라갔는지 성공/실패를 판단해야 했습니다.
  • 그런데 너무 빨리 판단하면, 화면에서는 아직 닿지 않았는데 코드에서는 이미 닿은 것처럼 계산될 수 있었습니다.
  • 또 게임을 나가거나 일시정지했는데, 잠시 뒤 실행되기로 예약된 다음 블록 생성이 계속 남아 있을 수 있었습니다.
설계 방향
  • SwiftUI에서 위치를 추측하지 않고, SpriteKit이 블록의 실제 물리 위치를 계산한 다음에 성공/실패를 판단하게 했습니다.

  • BlockItem은 startMoving, stopMoving, enableGravity, fixPosition처럼 노드 표현과 물리 바디 제어만 담당합니다.

override func didSimulatePhysics() {
  guard !isGamePaused else { return }
  guard let block = currentBlockView,
        let previousBlock = stackGame.previousBlock
  else { return }

  let targetY = previousBlock.positionY + previousBlock.height

  if block.position.y <= targetY {
    checkAlignmentAndHandle(targetY: targetY)
  }
}

func checkAlignmentAndHandle(targetY: CGFloat) {
  guard let block = currentBlockView else { return }

  stackGame.updateCurrentBlockPosition(
    positionX: block.position.x,
    positionY: targetY
  )

  if stackGame.checkAlignment() {
    block.fixPosition()
    block.position = CGPoint(x: block.position.x, y: targetY)
    placeBlockSuccess()
  } else {
    placeBlockFail()
  }
}

HM-02 · Mission System

게임은 결과만 기록하고, 32개 미션은 Record 기준으로 자동 갱신되게 했습니다.

문제 상황
  • 미션이 탭, 언어맞추기, 버그피하기, 데이터쌓기, 플레이 시간, 아이템 사용, 튜토리얼, 커리어 달성까지 32개로 늘었습니다.
  • 각 게임 안에 “이 미션도 완료됐나?” 조건을 넣으면 게임 규칙과 미션 정책이 서로 엉키게 됩니다.
  • 미션 화면에서 직접 값을 계산하면 저장, 복원, 정렬, 보상 상태가 여러 곳으로 흩어질 수 있었습니다.
설계 방향
  • 게임 객체는 성공, 실패, 획득 같은 결과만 Record.Event로 남기게 했습니다.
  • Record가 누적값을 갱신한 뒤, 매 기록마다 MissionSystem에 미션 갱신을 요청하게 했습니다.
  • 미션별 목표값과 완료 조건은 MissionFactory, MissionType, MissionConstants로 모았습니다.
구현 근거
  • TapGame, StackGame, LanguageGame, DodgeGame은 각각 record(.tap), record(.stackingSuccess)처럼 이벤트만 호출합니다.
  • MissionType.currentValue는 미션마다 필요한 Record 필드만 읽습니다.
  • Mission.update(record:)는 현재값을 갱신하고, 기본 조건은 currentValue >= targetValue로 판단합니다.
결과 또는 검증
  • 새 미션을 추가할 때 게임 화면이나 미니게임 로직을 다시 열지 않아도 되는 구조가 됐습니다.
  • MissionSystem이 완료 상태 정렬, 보상 수령, hasCompletedMission 배지 상태를 한 곳에서 관리합니다.
  • RecordDTO가 미션 상태를 id 기준으로 저장하고 복원해, 앱 재실행 뒤에도 진행 상태가 유지됩니다.
Game Result 게임은 이벤트만 기록 tap, stackingSuccess, languageCorrect, dodgeBugAvoid
→
Record 누적값을 한 곳에서 갱신 카운터 업데이트 후 MissionSystem에 전달
→
Mission System 32개 미션 완료 여부 판단 MissionFactory 조건, 정렬, 보상, 배지 상태 관리
핵심 변화 게임 로직은 미션을 몰라도 되고, 미션은 Record만 읽어서 완료 여부를 판단합니다.
Core Code 게임 이벤트를 Record로 모으고, 미션 조건은 MissionType과 MissionSystem에서만 판단했습니다.

Record: 이벤트를 단일 진입점으로 모으기

func record(_ event: Event) {
  switch event {
  case .tap(let count):
    totalTapCount += count
  case .stackingSuccess:
    stackingSuccessCount += 1
    stackConsecutiveSuccess += 1
  case .stackingFail:

    languageCorrectCount += 1
    languageConsecutiveCorrect += 1
  case .dodgeBugAvoid(let currentCombo):
    dodgeMaxCombo = max(currentCombo, dodgeMaxCombo)
  default:
    /* money, item, playTime, tutorial, career */
  }

  missionSystem.updateCompletedMissions(record: self)
}

var currentValue: (Record) -> Int {

  case .stackItem:

HM-03 · App Lifecycle

앱이 중단돼도 성장 상태와 미션 진행도를 잃지 않게 저장 경계를 분리했습니다.

문제 상황
  • 게임은 재화, 스킬, 장비, 미션, 기록처럼 계속 쌓이는 상태가 많았습니다.
  • 앱이 백그라운드로 내려가거나 종료될 때 저장하지 않으면 방금 얻은 보상과 미션 진행도가 사라질 수 있었습니다.
  • 화면 상태를 그대로 저장하려 하면 SwiftUI 상태, 게임 모델, 영속 데이터가 한데 섞일 위험이 있었습니다.
설계 방향
  • 저장은 앱 루트의 scenePhase 변화에서만 트리거하게 했습니다.
  • 화면 객체를 저장하지 않고, UserDTO, RecordDTO, MissionStateDTO처럼 복원에 필요한 값만 분리했습니다.
  • 실제 파일 저장과 로드는 UserRepository로 감춰 앱 루트가 저장 방식까지 알지 않게 했습니다.
구현 근거
  • SoloDeveloperTrainingApp은 .background, .inactive에서 saveUser()를 호출합니다.
  • FileManagerUserRepository는 UserDTO를 JSON으로 인코딩해 Documents의 user_data.json에 atomic write로 저장합니다.
  • RecordDTO.toRecord()는 32개 미션을 다시 만든 뒤, 저장된 MissionStateDTO를 id 기준으로 찾아 진행도와 상태를 복원합니다.
결과 또는 검증
  • 앱 실행 시 loadUser()가 저장된 사용자를 복원하고, 없으면 온보딩 흐름으로 진입합니다.
  • 재화, 인벤토리, 스킬, 기록, 미션 상태가 한 DTO 그래프로 저장되어 복원 기준이 명확해졌습니다.
  • 미션 정의는 코드에서 다시 생성하고, 사용자의 진행 상태만 덮어써 미션 목록 변경에도 대응하기 쉬워졌습니다.
Scene Phase 백그라운드/비활성 전환 감지 앱 루트에서 saveUser() 호출
→
DTO Boundary 복원에 필요한 값만 직렬화 UserDTO, RecordDTO, MissionStateDTO
→
Repository JSON 파일로 저장하고 다음 실행 때 복원 Documents/user_data.json, atomic write
핵심 변화 화면 상태가 아니라 사용자 진행 상태를 저장 단위로 삼아, 앱 종료와 재실행 사이의 데이터 손실을 줄였습니다.
Core Code scenePhase는 저장 시점만 결정하고, 실제 저장 구조는 Repository와 DTO가 맡게 했습니다.

App Root: 앱 상태 변화에서 저장 트리거

@Environment(\.scenePhase)
private var scenePhase

.onAppear {
  loadUser()
}
.onChange(of: scenePhase) { _, newPhase in
  if newPhase == .background ||
     newPhase == .inactive {
    saveUser()
  }
}

func saveUser() {
  guard let user = user else { return }
  Task {
    try await userRepository.save(user)
  }
}

Repository / DTO: 사용자 진행 상태만 저장

func save(_ user: User) async throws {
  let userDTO = UserDTO(
    id: user.id,
    nickname: user.nickname,
    career: CareerDTO(from: user.career),
    wallet: WalletDTO(from: user.wallet),
    inventory: InventoryDTO(from: user.inventory),
    record: RecordDTO(from: user.record),
    skills: user.skills.map { SkillDTO(from: $0) }
  )

  let url = fileURL
  let data = try JSONEncoder().encode(userDTO)

  Task.detached {
    try data.write(to: url, options: [.atomic])
  }
}

RecordDTO: 미션 정의와 진행 상태 분리

func toRecord() -> Record {
  let record = Record(
    missionSystem: MissionSystem(
      missions: MissionFactory.createAllMissions()
    )
  )

  record.totalTapCount = totalTapCount
  record.stackingSuccessCount = stackingSuccessCount
  record.stackConsecutiveSuccess = stackConsecutiveSuccess

  for missionState in missionStates {
    if let mission = record.missionSystem.missions
      .first(where: { $0.id == missionState.id }) {
      mission.currentValue = missionState.currentValue
      mission.state = missionState.state.toMissionState()
    }
  }

  return record
}
